# Задание 6. Сравнение моделей на сложной задаче предметной области

## Задача

**C1: подбор ближайших окон для записи к врачу.** Полный текст задачи —
[`prompts/task6-models/C1-prompt.md`](../prompts/task6-models/C1-prompt.md).

Функция должна учитывать:
- специальность врача;
- сетку слотов и смену;
- рабочие дни, выходные даты и перерывы;
- занятость врача и пациента, причём интервалы полуоткрытые;
- окно горизонта и ограничение числа результатов;
- проверку ввода;
- переходы на летнее и зимнее время (несуществующее и повторяющееся «настенное» время);
- производительность.

Это та же логика, что в сервисе записи приложения, только сложнее: добавлены несколько
врачей, перерывы, отпуска и переход на летнее время.

**Как проверялась правильность.** Решения проверяет скрытый набор из 34 тестов
[`comparison/task6/test_find_slots.py`](../comparison/task6/test_find_slots.py). Он
написан по спецификации до получения ответов и проверен на моём эталонном решении
[`reference_slots.py`](../comparison/task6/reference_slots.py), которое проходит все 34
теста. Модели тестов не видели.

**Условия у всех моделей одинаковые:**
- один и тот же текст запроса;
- отдельный экземпляр модели;
- без запуска кода — модель отвечает как в обычном чате;
- код из ответа берётся без правок скриптом
  [`evaluate.py`](../comparison/task6/evaluate.py).

**Итерации.** Если первое решение падает, модель получает список упавших тестов
(без их кода). Всего допускается не больше 3 итераций.

### Что различает модели

1. **Корректность одинакова, отличаются инженерные решения.** Все три модели Claude
   с первой попытки правильно обработали самые трудные места:
   - несуществующее время при переходе на летнее (проверка через обратный перевод в
     местное время);
   - повторяющееся время (`fold=0`);
   - полуоткрытые интервалы;
   - включительную верхнюю границу горизонта.

   Задача оказалась по силам всем трём крупным моделям, поэтому различия ниже касаются
   производительности, устойчивости и читаемости.
2. **Производительность.** Opus в 2–2,5 раза быстрее остальных. Он строит для каждого
   врача ленивый генератор окон в порядке времени и сливает их через `heapq.merge`, а
   затем `islice(limit)` останавливает перебор, как только набрано нужное число окон.
   Sonnet и Haiku сначала собирают все подходящие окна и только потом сортируют их. Мой
   эталон делает так же, поэтому он медленнее всех.
3. **Граничный ввод.** При `horizon_days = 10⁹` Opus и Sonnet падают с `OverflowError`
   внутри `timedelta`, хотя спецификация требует `ValueError` для ошибочных аргументов.
   Haiku возвращает результат благодаря раннему выходу. В худшем случае (свободных окон
   нет, горизонт 100 лет) все три укладываются в 0,3 с.
4. **Скрытый дефект Haiku.** Аннотация `tz: ZoneInfo` ссылается на имя без импорта.
   Код работает только потому, что включено `from __future__ import annotations`, а
   `typing.get_type_hints()` или проверка типов на этом упадут. Тесты такое не ловят,
   нашёл линтер.
5. **Локальная 3b-модель задачу не решила.**
   - На итерациях 1 и 2 генерация зациклилась: функции с растущими именами вида
     `is_work_time_and_not_busy_and_not_patient_busy_and_…` шли до лимита 4096 токенов.
   - На итерации 3 начат новый диалог с `repeat_penalty 1.2` (штатная защита Ollama от
     повторов; это единственное отличие условий). Код получился без цикла, но модуль не
     импортируется: `ZoneInfo` используется без импорта, ещё 9 неопределённых имён.

## Вывод

Для сложной предметной логики с часовыми поясами и граничными случаями крупные
облачные модели дают корректный код с первой итерации. Выбирать между ними стоит по
вторичным критериям:
- Opus — самый производительный и самый структурированный код, но отвечает дольше;
- Sonnet отвечает быстрее всех, но пишет менее читаемо (одна большая функция);
- Haiku — хорошая структура, но с мелким дефектом аннотаций.

Маленькая локальная модель (3B, 4 ГБ видеопамяти) подходит для автодополнения и
коротких фрагментов (см. задание 3), но для такой задачи непригодна: она теряет
связность длинного ответа.

Во всех случаях решение нужно проверять независимыми тестами. Ни одна модель не
указала, что её код падает с `OverflowError` на огромном горизонте, а дефект аннотации у
Haiku тесты вообще не ловят.
