# P3 — связанные сущности, медицинские данные, аналитика, управление пользователями

Модель: Claude Sonnet 5.5 (отдельный экземпляр). Доступ: только чтение текущего кода
`app/` — того, что сгенерировано в P1 и P2, вместе с моими исправлениями после ревью.

Почему так: после P2 видно, что модель хорошо следует пронумерованным правилам, но
выполняет их буквально (находка №3 в `reports/code-review.md`: отмену прошедшего
приёма промпт явно не запретил, и модель её разрешила). Поэтому здесь для каждого
действия заданы не только роли, но и условия: кто, над чем и когда. Отдельный блок
посвящён доступу к медицинским данным. Регистратор и администратор работают с
расписанием и учётными записями, а не с диагнозами, поэтому медкарты и рецепты им
закрыты. Для аналитики потребовано считать агрегаты в SQL, а не циклом в Python, и
ограничить период: без этого модель легко пишет «загрузить всё и посчитать».

## Текст промпта

```text
Ты — senior Python backend-разработчик. Продолжаешь проект «Система управления
клиникой» (FastAPI, SQLAlchemy 2.0 async, Pydantic v2).

Контекст: прочитай весь текущий код в каталоге app/ (config, db, models, schemas,
security, errors, services/scheduling, services/appointments, routers/auth,
routers/appointments, main). Повторяй принятые там решения: доменные исключения из
app/errors.py, транзакции коммитит сервисный слой, связи lazy="raise" загружаются
явно, чужой объект для пользователя без доступа — 404, время — aware UTC, «сейчас» —
через зависимость get_now. Существующие файлы не переписывай; исключение — app/main.py
(подключить новые роутеры): его приведи целиком. Готовые схемы Create/Update/Out из
app/schemas.py используй как есть; новые схемы (аналитика и т. п.) положи в новый
файл app/schemas_extra.py.

Задача: остальные сущности, доступ к медицинским данным, аналитика и управление
пользователями.

1. Пользователи — app/routers/users.py, только admin:
   - GET /api/users — фильтры role, is_active, поиск q по email и ФИО (без учёта
     регистра), пагинация limit/offset;
   - POST /api/users — создать пользователя с любой ролью;
   - PATCH /api/users/{id} — ФИО, email, пароль, роль, is_active.
   Ограничения: администратор не может снять роль admin или деактивировать сам себя
   (защита от потери доступа к системе); нельзя сменить роль, если у пользователя есть
   профиль Doctor или Patient, не соответствующий новой роли, — 409.

2. Врачи — app/routers/doctors.py:
   - GET /api/doctors (фильтр specialty) и GET /api/doctors/{id} — все
     аутентифицированные; в ответе также ФИО врача; деактивированные врачи в списке не
     показываются;
   - POST /api/doctors — admin: профиль для пользователя с ролью doctor, у которого
     профиля ещё нет;
   - PATCH /api/doctors/{id} — admin: кабинет, специальность, график. Если новый график
     (дни, смена, длина слота) оставляет будущие записи scheduled вне смены или вне
     сетки — 409, в сообщении число таких записей; график не меняется.

3. Пациенты — app/routers/patients.py:
   - admin, registrar: GET /api/patients (поиск q по ФИО и номеру полиса, пагинация),
     GET /api/patients/{id}, POST, PATCH (в том числе привязка user_id: пользователь
     должен иметь роль patient и не быть привязан к другому пациенту);
   - patient: GET /api/patients/me — свой профиль;
   - doctor: GET /api/patients/{id} — только пациент, у которого есть хотя бы одна
     запись к этому врачу (любой статус, кроме cancelled); иначе 404.

4. Медицинские данные — рецепты и медкарты: app/routers/prescriptions.py,
   app/routers/medical_records.py. Доступ строже, чем к расписанию:
   - читать: врач — данные пациентов, у которых он вёл приём (есть запись в статусе
     completed); пациент — только свои; admin и registrar — НЕТ доступа (403):
     они работают с расписанием, а не с диагнозами;
   - Prescription создаёт только врач этой записи, запись должна быть в статусе
     completed; редактирование и удаление рецептов не предусмотрено (выписанный
     рецепт не меняется);
   - MedicalRecord создаёт только врач; если указан appointment_id, запись должна
     быть completed, принадлежать этому врачу и этому пациенту; если не указан — врач
     должен был вести хотя бы один completed-приём этого пациента. doctor_id берётся из
     профиля текущего врача, а не из тела запроса (тело может содержать doctor_id
     из схемы MedicalRecordCreate — тогда он должен совпадать с текущим врачом, иначе
     403);
   - PATCH MedicalRecord — только автор и только в течение 24 часов после создания;
     удаление не предусмотрено;
   - эндпоинты: POST /api/prescriptions, GET /api/appointments/{id}/prescriptions,
     POST /api/medical-records, GET /api/patients/{id}/medical-records (сортировка
     по created_at, новые первыми), PATCH /api/medical-records/{id}.

5. Аналитика — app/routers/analytics.py и app/services/analytics.py, роли admin и
   registrar (агрегаты без персональных и медицинских данных отдельных людей):
   - GET /api/analytics/summary?date_from&date_to — число записей по статусам, доля
     неявок no_show / (completed + no_show), доля отмен;
   - GET /api/analytics/doctors-load?date_from&date_to — по каждому врачу: доступные
     минуты по графику за период, занятые минуты (записи не cancelled), загрузка в
     процентах, число completed и no_show;
   - GET /api/analytics/appointments-per-day?date_from&date_to — число записей по
     местным датам клиники (дни без записей — с нулём);
   - GET /api/analytics/top-diagnoses?date_from&date_to&limit — самые частые коды
     МКБ-10 (только код и количество).
   Даты — местные даты клиники, включительно; период не длиннее 366 дней, иначе 422.
   Подсчёт — агрегатами в SQL (GROUP BY), а не загрузкой всех строк в Python.
   Доступные минуты по графику — чистая функция без БД (её удобно тестировать).

Требования к коду: type hints; docstring у модулей и неочевидных функций; права на
уровне объектов проверяет сервисный слой; никаких N+1 запросов в списках. Тесты не
пиши — они будут в отдельном запросе.

Формат ответа: для каждого файла — заголовок `### путь/к/файлу` и один блок кода с
полным содержимым файла. После файлов — короткий список допущений и отдельный список
мест, которые стоит особенно внимательно проверить на ревью.
```
