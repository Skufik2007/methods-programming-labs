# P2 — аутентификация и записи на приём (основная бизнес-логика)

Модель: Claude Sonnet 5.5 (отдельный экземпляр). Доступ: только чтение пяти файлов,
полученных в P1, — так же в IDE-ассистент попадают открытые файлы проекта.

Почему так: в P1 модель сама перечислила в допущениях, что частичный индекс не
защищает от пересечения интервалов, рабочих часов и переходов статусов, — это работа
сервисного слоя. Поэтому здесь правила расписания заданы явно и пронумерованы, чтобы
их можно было проверить по одному. Чистая логика расписания (без БД) отделена от
работы с БД, чтобы её было удобно тестировать. Отдельно оговорены неочевидные места
безопасности: тайминг-атака на логин, привязка аккаунта к чужой медкарте по номеру
полиса, утечка факта существования чужой записи (404 вместо 403).

## Текст промпта

```text
Ты — senior Python backend-разработчик. Продолжаешь проект «Система управления
клиникой» (FastAPI, SQLAlchemy 2.0 async, Pydantic v2, PyJWT, bcrypt).

Контекст: в проекте уже есть файлы app/config.py, app/db.py, app/models.py,
app/schemas.py, app/security.py — прочитай их и опирайся на их интерфейсы
(Settings.clinic_tz, get_session, модели и enum'ы, схемы Create/Update/Out,
hash_password_async / verify_password_async, create_access_token, CurrentUser,
require_roles). Эти файлы не переписывай. Если без изменения какого-то из них не
обойтись — приведи его новую версию целиком и объясни причину.

Задача: аутентификация и основная сущность — записи на приём (Appointment) с
бизнес-правилами и проверкой прав.

Нужны файлы:
1. app/__init__.py, app/services/__init__.py, app/routers/__init__.py — пакеты.
2. app/errors.py — доменные исключения (NotFoundError, ConflictError,
   PermissionDeniedError, BusinessRuleError) и функция регистрации обработчиков,
   превращающих их в HTTP 404 / 409 / 403 / 422 с телом {"detail": "..."}.
3. app/services/scheduling.py — чистые функции без БД и без FastAPI:
   - проверка, что интервал [starts_at, ends_at) лежит в рабочем дне и смене врача
     (work_days, work_start, work_end — местное время клиники, переводить через
     zoneinfo, интервал не переходит через полночь);
   - проверка сетки: starts_at совпадает с началом слота (от work_start с шагом
     slot_minutes), длительность — от 1 до 4 слотов;
   - пересекаются ли два полуоткрытых интервала;
   - список свободных слотов врача на дату (местную) с учётом занятых интервалов
     и текущего момента (прошедшие слоты не предлагать).
   Текущее время передаётся параметром, а не берётся внутри (для тестов).
4. app/services/appointments.py — операции с БД: создать, получить, список с
   фильтрами, перенести, сменить статус. Транзакции коммитит этот слой.
5. app/routers/auth.py:
   - POST /api/auth/register — самостоятельная регистрация пациента: email, пароль,
     ФИО, дата рождения, телефон, полис ОМС. Создаёт User(role=patient) и Patient
     в одной транзакции. Если пациент с таким полисом уже есть — 409, аккаунт к
     нему НЕ привязывается (иначе любой, кто знает номер полиса, получит доступ к
     чужой медкарте; привязку делает регистратор). Занятый email — 409.
   - POST /api/auth/login — JSON {email, password} → TokenOut. Одинаковый ответ 401
     для «нет пользователя», «неверный пароль» и «деактивирован»; при отсутствии
     пользователя всё равно выполнить проверку bcrypt по фиктивному хэшу (защита
     от определения существующих email по времени ответа).
   - GET /api/auth/me — текущий пользователь (UserOut).
6. app/routers/appointments.py:
   - GET /api/appointments — фильтры doctor_id, patient_id, status, date_from,
     date_to; пагинация limit (1..100, по умолчанию 20) и offset; сортировка по
     starts_at.
   - GET /api/appointments/{id}
   - POST /api/appointments
   - PATCH /api/appointments/{id} — перенос (starts_at/ends_at) и причина.
   - POST /api/appointments/{id}/cancel, /complete, /no-show — смена статуса.
   - GET /api/doctors/{doctor_id}/slots?date=YYYY-MM-DD — свободные слоты.
7. app/main.py — фабрика create_app(), lifespan с dispose_engine(), подключение
   роутеров и обработчиков ошибок, GET /api/health.

Бизнес-правила записи (каждое — отдельная проверка с понятным сообщением):
П1. Запись только в будущее и не дальше чем на 90 дней вперёд.
П2. Интервал внутри рабочего дня и смены врача, по сетке слотов (см. scheduling).
П3. Не пересекается с неотменёнными записями этого врача (пересечение интервалов,
    а не только совпадение начала) — 409.
П4. Не пересекается с неотменёнными записями этого же пациента — 409.
П5. К деактивированному врачу (user.is_active = false) записаться нельзя.
П6. Гонка двух одновременных записей: в PostgreSQL перед проверкой П3 заблокировать
    строку врача (SELECT ... FOR UPDATE); IntegrityError от уникального индекса
    превращать в 409, а не в 500.
П7. Переходы статусов: scheduled → completed | no_show | cancelled; из completed,
    no_show, cancelled — никуда. completed и no_show — только после начала приёма.
П8. Перенос — только для scheduled, с теми же проверками П1–П6 (саму запись при
    поиске пересечений исключить).
П9. created_by — id текущего пользователя, из тела запроса не принимается.

Права:
- admin, registrar — все записи: создание, перенос, отмена.
- doctor — видит только свои записи; ставит completed / no_show только своим.
- patient — видит только свои записи; создаёт запись только для своего профиля
  Patient; отменяет и переносит свою запись не позже чем за 2 часа до начала.
- Чужая запись для doctor и patient — 404 (не раскрывать факт существования).
- Слоты врача видят все аутентифицированные пользователи.

Требования к коду: type hints везде; docstring у модулей и неочевидных функций;
async-код без блокирующих вызовов; связи моделей объявлены с lazy="raise", поэтому
загружать их явно; время — только timezone-aware UTC. Тесты не пиши — они будут в
отдельном запросе.

Формат ответа: для каждого файла — заголовок `### путь/к/файлу` и один блок кода с
полным содержимым файла. После файлов — короткий список допущений и отдельный список
мест, которые стоит особенно внимательно проверить на ревью.
```
