## Записи по заданиям варианта 3

### 1. Средн. №3 — валидация входных данных в Go

| | |
|---|---|
| **Задача для AI** | Проверка заказа (покупатель, позиции, доставка) в Go-сервисе на Gin с понятными клиенту ошибками. |
| **Что предложил AI** | Правила тегами `binding` валидатора Gin и собственные правила `sku`, `money` (2 знака), `delivery_date` (сегодня…+90 дней), проверка уникальности SKU. Пути полей в ошибках как в JSON (`items[0].sku`), сообщения на русском. Разные коды: 400 — разбор JSON, 413 — размер, 422 — правила. Сумма считается в копейках. |
| **Принято** | Набор правил и формат ошибок. Python-сервис повторяет те же правила на Pydantic. |
| **Изменено после проверки** | Обрезанный JSON давал `bad_request` — исправлено на `invalid_json`. Для невалидного повторного SKU возвращались две ошибки — оставлена одна. **На итоговом ревью:** имя и адрес из одних пробелов больше не проходят (правило `notblank`); встроенное правило email заменено общим с Python шаблоном; «сегодня» считается по UTC, как в Python; чужой заказ отвечает 404, чтобы не раскрывать чужие id. |
| **Как проверено** | 12 пограничных случаев прогоняются через настоящий Go и Python со сравнением статуса, кода и набора `(поле, правило)`. Эта проверка выявила четыре расхождения между сервисами, все устранены. |

### 2. Средн. №5 — передача сложных структур данных (JSON) между сервисами

| | |
|---|---|
| **Задача для AI** | Обмен вложенными структурами между Python и Go в обе стороны. |
| **Как появилось задание** | В первоначальной таблице его не было. Когда я передал обновлённую таблицу, при сверке выяснилось, что обмен был реализован лишь частично: Python брал из ответа Go пару полей как из словаря. Задание доведено до полноценного. |
| **Что предложил AI** | `POST /api/v1/orders` в Python: проверка вложенного заказа и передача в Go (даты строками, без `null`). Ответы Go разбираются по типизированному контракту (`app/contract.py`) с проверкой согласованности: сумма должна сходиться с позициями. Нарушение контракта — 502 с указанием поля. Сводка агрегирует вложенные позиции по SKU. |
| **Принято** | Контракт и оба направления обмена. |
| **Изменено после проверки** | Ошибки Go 401/403/422 пробрасываются одинаково в обоих эндпоинтах (в сводке раньше превращались в 502); тело не в общем формате ошибок даёт 502, а не 500. Расчёт копеек вынесен в один модуль. |
| **Как проверено** | Сквозной тест на настоящем Go: заказ с кириллицей, «кавычками», эмодзи и суммой до 10 млн проходит Python → Go → Python без искажений. |

### 3. Средн. №7 — graceful shutdown в обоих сервисах

| | |
|---|---|
| **Задача для AI** | Корректная остановка Go- и Python-сервиса без потери активных запросов. |
| **Что предложил AI** | Одинаковый порядок в обоих сервисах: `/health/ready` → 503, пауза `DRAIN_DELAY`, ожидание активных запросов до `SHUTDOWN_TIMEOUT`, затем освобождение ресурсов. |
| **Принято** | Схема остановки и тесты на настоящем сокете. |
| **Изменено после проверки** | Тест Python падал без сообщения: uvicorn повторно поднимал пойманный SIGTERM и завершал процесс pytest. Добавлена программная остановка `begin_shutdown()`. **На итоговом ревью:** `SHUTDOWN_TIMEOUT=0.5` превращался в бесконечное ожидание (`int(0.5) or None`) — значение теперь передаётся без округления, `0` означает «не ждать», как в Go. |
| **Как проверено** | Юнит-тесты в обоих сервисах; в CI `docker compose stop` останавливает контейнеры по SIGTERM без SIGKILL. |

### 4. Повыш. №3 — JWT-аутентификация в Go, проверка токенов из Python

| | |
|---|---|
| **Задача для AI** | Go выдаёт токены, Python их проверяет. |
| **Что предложил AI** | Подпись **RS256 с публикацией ключа через JWKS** вместо общего секрета: Python может проверить токен, но не может его подделать. Проверки: только RS256 (защита от `alg=none` и подмены на HS256), `iss`, `aud`, обязательный `exp`. В Python ключи кешируются, при неизвестном `kid` кеш обновляется не чаще раза в 30 с. |
| **Принято** | Асимметричная схема: сервисам на разных языках не нужно делить общий секрет. |
| **Добавлено на итоговом ревью** | Ограничение подбора паролей: 5 неудач для пары «имя + IP» дают блокировку на 5 минут (429 и `Retry-After`); `X-Forwarded-For` от клиента не учитывается. Ключ подписи сохраняется в файл, поэтому токены переживают перезапуск Go. Python работает на известных ключах, пока Go недоступен, и проверяет формат JWKS. |
| **Как проверено** | Тесты с обеих сторон на подделанные, истёкшие и чужие токены; в CI токен, выданный до перезапуска go-api, принимается после него. Тест на `Retry-After` сначала падал на медленном runner — точное значение заменено диапазоном. |

### 5. Повыш. №5 — оба сервиса в Docker Compose с общей сетью

| | |
|---|---|
| **Задача для AI** | Развернуть Go и Python в compose с общей сетью. |
| **Что предложил AI** | Многоэтапные образы: Go — статический бинарь в distroless (24 МБ), Python — venv в slim-образе. Healthcheck выполняет сам бинарь (в образе нет curl). Сеть `lab10-backend`, Python обращается к Go по имени `go-api`, стартует после healthy go-api. |
| **Моё решение** | Проверка в GitHub Actions: сборка, DNS внутри сети, сквозной smoke-тест, остановка по SIGTERM. |
| **Изменено на итоговом ревью** | Базовые образы закреплены по digest; ключ JWT хранится в volume `jwt-keys`. |
| **Не добавлено** | Dependabot для автообновления digest: он сам открывал бы pull request в репозитории. Вместо этого в Dockerfile описано, как обновить digest вручную. |
