## Описание решения

### Средн. №3. Валидация входных данных в Go

Модель `CreateRequest` описывает заказ: покупатель, позиции и доставка. Правила заданы тегами `binding` того же валидатора `go-playground/validator`, который использует Gin:

| Поле | Правила |
|---|---|
| `customer.name` | обязательно, 2–100 символов, собственное правило `notblank`: не из одних пробелов |
| `customer.email` | обязательно, ≤ 254, email по шаблону HTML (WHATWG) с обязательной точкой в домене |
| `customer.phone` | необязательно (пустая строка = не указан), формат E.164 (`+79991234567`) |
| `items` | 1–50 позиций, SKU не повторяются |
| `items[].sku` | собственное правило `sku`: `ABC-123` (3 заглавные буквы, дефис, 3–6 цифр) |
| `items[].quantity` | 1–100 |
| `items[].price` | > 0, ≤ 1 000 000, собственное правило `money`: не больше 2 знаков после запятой |
| `delivery.address` | обязательно, 5–300 символов, `notblank` |
| `delivery.date` | собственное правило `delivery_date`: `YYYY-MM-DD`, от сегодняшней даты по UTC до +90 дней |
| `comment` | ≤ 500 символов |

Особенности:
- **Имена полей в ошибках — как в JSON** (`items[0].sku`, а не `Items[0].SKU`): для этого зарегистрирована функция имени тега.
- **Разные коды для разных ошибок:** `400` — синтаксис JSON, неверный тип или неизвестное поле (`DisallowUnknownFields`), `413` — тело больше 1 МБ (в том числе переданное частями без `Content-Length`), `422` — нарушение правил, со списком `details` из `{field, rule, message}` на русском.
- **Сумма считается в копейках** (`int64`): иначе `0.1 + 0.2` во float даёт ошибку округления.
- **«Сегодня» — по UTC** в обоих сервисах: по местному времени Go и Python ночью расходились бы на сутки.
- **Чужой заказ отвечает 404**, как несуществующий: 403 подтвердил бы, что заказ с таким id существует.

```json
{"error": {"code": "validation_failed", "message": "данные не прошли проверку", "details": [
  {"field": "items[0].sku", "rule": "sku", "message": "SKU в формате ABC-123 (три заглавные латинские буквы, дефис, 3–6 цифр)"},
  {"field": "items[0].price", "rule": "money", "message": "не больше двух знаков после запятой"}]}}
```

FastAPI-сервис проверяет заказ теми же правилами на Pydantic (`python/app/models.py`) и отдаёт ошибки в том же формате; шаблоны SKU, телефона и email в обоих сервисах одинаковые. Сквозной тест `test_same_validation_rules` прогоняет 12 пограничных случаев (цена больше миллиона, `ivan@ex..com`, пустой телефон, имя из пробелов, дробное количество, повтор SKU и др.) через настоящий Go-сервис и Python и сверяет статус, код ошибки и набор `(поле, правило)`. Проверка этих случаев выявила четыре расхождения (имя правила для цены, email вида `ivan@ex..com`, пустой телефон, путь поля при повторе SKU) — все устранены, тест закрепляет результат.

### Средн. №5. Передача сложных структур данных (JSON) между сервисами

Между сервисами передаётся заказ — вложенная структура из покупателя, списка позиций и доставки:

```json
{
  "id": "1b9d6bcd-bbfd-4b2d-9b5d-ab8dfbbd4bed",
  "owner": "student",
  "customer": {"name": "Иван Петров", "email": "ivan@example.com", "phone": "+79991234567"},
  "items": [
    {"sku": "ABC-123", "quantity": 2, "price": 199.99},
    {"sku": "DEF-4567", "quantity": 1, "price": 50}
  ],
  "delivery": {"address": "Москва, ул. Пушкина, 1", "date": "2026-10-12"},
  "comment": "Позвонить за час",
  "total_cents": 44998,
  "total": 449.98,
  "created_at": "2026-10-09T12:00:00Z"
}
```

| Направление | Как передаётся |
|---|---|
| **Python → Go** | `POST /api/v1/orders` в Python: Pydantic проверяет вложенную структуру по тем же правилам, что в Go, и сериализует её через `model_dump(mode="json", exclude_none=True)`. `date` превращается в `"YYYY-MM-DD"`, отсутствующий телефон не уходит как `null`. Go проверяет заказ ещё раз (защита в глубину). Ошибки Go 401/403/422 Python отдаёт клиенту без изменений (вместе с `WWW-Authenticate`): формат ошибок у сервисов общий. Тело не в этом формате (например, HTML-страница прокси) даёт 502, а не 500. |
| **Go → Python** | Ответы `POST` и `GET /api/v1/orders` разбираются не как `dict`, а по моделям-контракту [`python/app/contract.py`](python/app/contract.py) (`GoOrder`, `GoCustomer`, `GoItem`, `GoDelivery`, `GoOrdersPage`). `id` становится `UUID`, даты — `date`/`datetime`, `quantity` должно быть строго целым. |

Особенности контракта:
- **Проверяется согласованность вложенных данных:** `total_cents` должен совпадать с суммой позиций, `count` — с длиной списка.
- **Нарушение контракта** (нет поля, не тот тип, не сходится сумма) даёт ответ **502 `upstream_contract_violation`** с указанием поля, а не 500 с `KeyError` в глубине обработчика.
- **«Терпимый читатель»:** незнакомые поля игнорируются (`extra="ignore"`), поэтому новое поле в ответе Go не ломает Python.
- **Деньги передаются в копейках** (`int64` в Go ↔ `int` в Python), поэтому суммы до 10 млн проходят без ошибок округления float.
- `GET /api/v1/orders/summary` агрегирует вложенные позиции всех заказов по SKU (`by_sku`) и возвращает последний заказ целиком (`last_order`).
- В каждый запрос к Go пробрасываются токен пользователя и `X-Request-ID`, по которому связываются логи двух сервисов.

Тесты:
- **с поддельным Go** ([`tests/test_summary.py`](python/tests/test_summary.py)): что именно получил Go; разбор ответа; проброс ошибок Go; 502 при нарушении контракта; агрегация по SKU;
- **с настоящим Go** ([`tests/test_integration_go.py`](python/tests/test_integration_go.py)): заказ с кириллицей, «кавычками», эмодзи 📦, экранированием и позицией 100 × 999 999.99 создаётся через Python, а затем совпадает с тем, что Go отдаёт напрямую.

### Средн. №7. Graceful shutdown в обоих сервисах

Порядок остановки одинаковый в Go и Python:

1. По SIGINT/SIGTERM `/health/ready` сразу начинает отвечать **503**, а `/health/live` остаётся 200. Балансировщик или оркестратор перестаёт слать новые запросы, но не перезапускает процесс.
2. Выдерживается пауза **`DRAIN_DELAY`**: сервер ещё принимает запросы, пока все узнают о 503.
3. Слушающий сокет закрывается, простаивающие keep-alive соединения закрываются, **активные запросы дорабатывают** в пределах `SHUTDOWN_TIMEOUT`.
4. Если время вышло, оставшиеся соединения закрываются принудительно (Go) или задачи отменяются (uvicorn). `SHUTDOWN_TIMEOUT` принимает дробные значения, `0` означает «не ждать» — одинаково в обоих сервисах.
5. Освобождаются ресурсы. В Python lifespan закрывает HTTP-клиент к Go только после того, как завершились запросы.

| | Go (`internal/server`) | Python (`app/server.py`) |
|---|---|---|
| сигнал | `signal.NotifyContext` | `uvicorn.Server.handle_exit` (переопределён) |
| ожидание запросов | `http.Server.Shutdown(ctx)` | `timeout_graceful_shutdown` uvicorn |
| drain | `time.Sleep(DrainDelay)` перед `Shutdown` | переопределённый `shutdown()` |
| тесты | активный запрос завершается, тайм-аут срабатывает, drain выдерживается | то же на настоящем сокете uvicorn |

В контейнерах оба процесса запускаются exec-формой (`ENTRYPOINT ["/server"]`, `CMD ["python", "-m", "app"]`), поэтому SIGTERM от `docker stop` приходит прямо в приложение. `stop_grace_period: 30s` в compose больше, чем `DRAIN_DELAY + SHUTDOWN_TIMEOUT`, чтобы Docker не прислал SIGKILL раньше. В CI `docker compose stop` занимает 5 с (два раза по drain в 2 с), в логах обоих сервисов есть записи о graceful shutdown и штатной остановке.

### Повыш. №3. JWT в Go-сервисе, проверка токенов из Python

**Go (выпуск):**
- `POST /auth/login` проверяет пароль (хеши bcrypt). Для несуществующего пользователя тоже выполняется сравнение bcrypt, поэтому по времени ответа нельзя понять, есть ли такой логин.
- Токен RS256 содержит `iss`, `aud`, `sub`, `role`, `iat`, `nbf`, `exp`, `jti`, а в заголовке — `kid`.
- `GET /.well-known/jwks.json` отдаёт открытый ключ (RFC 7517). `kid` вычисляется из хеша ключа, поэтому одинаков после перезапуска.
- **Ограничение подбора паролей:** 5 неудачных входов подряд для пары «имя + IP» блокируют вход на 5 минут (429 + `Retry-After`). IP в ключе не даёт со своего адреса заблокировать чужую учётную запись, а `X-Forwarded-For` от клиента не учитывается — иначе подменой заголовка ограничение обходилось бы.
- **Ключ подписи сохраняется** в `JWT_PRIVATE_KEY_FILE` (создаётся при первом запуске, права 0600), поэтому после перезапуска Go выданные токены остаются действительными. В CI это проверяется: токен, полученный до `docker compose restart go-api`, после него принимают и Go, и Python.
- Middleware проверяет `Authorization: Bearer`. Принимается только RS256, это защищает от `alg=none` и подмены на HS256 с открытым ключом в роли секрета. Проверяются `iss`, `aud`, обязательный `exp`, допуск 30 с на расхождение часов. При ошибке ответ 401 с `WWW-Authenticate` по RFC 6750.

**Python (проверка), `app/auth.py`:**
- `JWKSVerifier` скачивает JWKS из Go и проверяет подпись и claims через PyJWT с теми же требованиями (только RS256, `iss`, `aud`, `exp`, `sub`).
- Ключи кешируются на `JWKS_CACHE_TTL`. При неизвестном `kid` (Go сменил ключ) кеш обновляется, но **не чаще раза в 30 с**: иначе поток мусорных токенов превратился бы в DoS на Go-сервис.
- Если Go недоступен, а TTL кеша истёк, токены с уже известным `kid` принимаются по сохранённому ключу; повтор обновления — не чаще раза в 30 с. Если ключа нет совсем — 503 `auth_unavailable`, а не 401: токен может быть валидным.
- Ответ JWKS проверяется на формат `{"keys": [...]}` — некорректный даёт понятную ошибку, а не 500.
- `GET /api/v1/me` возвращает данные из токена, проверенного в Python (`verified_by: python:jwks`). `GET /api/v1/orders/summary` передаёт тот же токен и `X-Request-ID` в Go и собирает сводку по заказам пользователя.

Тесты с обеих сторон проверяют отказ для истёкшего токена, чужих `aud`/`iss`, отсутствия `exp`/`sub`, чужой подписи, `alg=none`, атаки HS256 с открытым ключом и мусора, а также ротацию ключа и ограничение частоты обновления JWKS.

### Повыш. №5. Оба сервиса в Docker Compose с общей сетью

- **Go-образ:** многоэтапная сборка, статический бинарь (`CGO_ENABLED=0`), финальный образ `distroless/static:nonroot` без shell. В CI его размер **24 МБ**. Healthcheck выполняет сам бинарь (`/server -healthcheck`), потому что curl в образе нет.
- **Python-образ:** зависимости ставятся в venv на этапе сборки, в финальный `python:3.12-slim` копируются только venv и код, процесс работает от непривилегированного пользователя. Размер **190 МБ**.
- **Базовые образы закреплены по digest** (`golang:1.27-alpine@sha256:…`): тег со временем указывает на другой образ, digest — всегда на один и тот же, поэтому сборка воспроизводима.
- **Ключ JWT в volume `jwt-keys`:** каталог `/keys` в образе принадлежит nonroot, Docker копирует его владельца в пустой volume, и сервис создаёт там ключ при первом запуске.
- **Слои под кеш:** сначала копируются файлы зависимостей (`go.mod/go.sum`, `requirements.txt`) и выполняется их загрузка с BuildKit cache mount, и только потом код. `.dockerignore` пропускает в контекст только нужное.
- **Сеть `lab10-backend`:** оба сервиса подключены к общей bridge-сети. Python обращается к Go по имени сервиса `http://go-api:8080` через встроенный DNS Docker. `py-api` стартует только после того, как `go-api` прошёл healthcheck (`depends_on: condition: service_healthy`).

Job `compose` в CI собирает образы, ждёт healthcheck обоих сервисов (`--wait`), проверяет DNS внутри сети, прогоняет [`deploy/smoke_test.py`](deploy/smoke_test.py) (вход → проверка токена в Python → заказ в Go → заказ через Python → сводка по SKU из Python через сеть compose) и проверяет graceful остановку контейнеров.

## Дополнительно: сравнение производительности и памяти

Этого задания нет в варианте 3, но оно отвечает на главный вопрос цели работы — чем на практике отличаются FastAPI и Gin.

**Нагрузочный тест** (`bench/run_bench.py`) запускает оба сервиса отдельными процессами с выключенным логом запросов. Затем для двух сценариев — `GET /ping` и `POST /api/v1/orders/validate` (разбор и валидация заказа из 3 позиций) — при 1, 16 и 64 параллельных соединениях он прогоняет генератор нагрузки `go/cmd/loadgen` и раз в 50 мс снимает память процесса. Перцентили задержки считаются методом nearest-rank. wrk и ab под Windows нет, а генератор на Python сам стал бы узким местом, поэтому генератор написан на Go.

**Микробенчмарки:** `go test -bench -benchmem` (время и аллокации на валидацию и на запрос через роутер Gin) и `bench/micro_validate.py` (Pydantic, пиковая память через `tracemalloc`).

### Выводы по производительности

- **Пропускная способность.** При одном соединении Gin быстрее FastAPI в 1.8–1.9 раза: в основном сказывается задержка сети и цикла событий. Под параллельной нагрузкой разрыв растёт до **7 раз** на Linux (на Windows — до 11): Go обрабатывает запросы горутинами на всех ядрах, а один процесс uvicorn упирается в GIL и одно ядро. Это видно и по p99: у FastAPI при c=64 задержка растёт почти линейно, так как запросы ждут в очереди цикла событий.
- **Узкое место Python — не Pydantic.** Сама валидация на Pydantic (ядро на Rust) медленнее Go-валидатора всего в 3.4 раза, а весь запрос — в 7 раз. Основное время уходит на ASGI-стек (uvicorn → Starlette → FastAPI → сериализация ответа).
- **Масштабирование Python процессами** (4 воркера uvicorn) дало прирост в 2.3 раза при 4 ядрах, но стоило в 4.6 раза больше памяти: каждый процесс несёт свой интерпретатор и копию всех модулей. Gin при этом всё равно быстрее в 3 раза и занимает в 10 раз меньше памяти.
- **Память.** Go-сервис в простое занимает около 20 МБ RSS и под нагрузкой растёт до 28 МБ. Python — около 64 МБ, и почти всё это стоимость загруженных модулей (FastAPI, Pydantic, cryptography), а не данных. Рост под нагрузкой у обоих небольшой: оба сервиса не держат состояние на запрос.
- **Итог.** Gin выгоден, когда важны плотность размещения и задержки под нагрузкой. FastAPI выигрывает скоростью разработки: валидация, документация Swagger/OpenAPI и асинхронный клиент «из коробки». Для большинства сервисов его 2–4 тыс. RPS на процесс более чем достаточно.

## Итоги

- Тесты: **Go** — 35 тестов и 36 подтестов (`-race` в CI), **Python** — 73 теста, включая сквозные с настоящим Go-сервисом и 12 случаев сравнения валидации Go и Python.
- CI (`.github/workflows/ci.yml`) проходит линтеры (gofmt, go vet, ruff), тесты, нагрузочный прогон на Linux с публикацией таблиц в summary и проверку Docker Compose.
- Go и Gin требуют больше явного кода: регистрация валидаторов, перевод ошибок, ручная обработка ошибок разбора JSON. Взамен они дают в 7 раз большую пропускную способность и в 3 раза меньший расход памяти.
- FastAPI и Pydantic описывают те же правила короче и сразу генерируют OpenAPI (`/docs`). Асинхронность помогает ждать сеть (запрос к Go в `/summary`), но не ускоряет вычисления: для CPU-работы Python масштабируется только процессами.
- Сложные вложенные структуры передаются между сервисами по явному контракту: Python проверяет и ответы Go, поэтому расхождение форматов обнаруживается сразу (502 с указанием поля), а не превращается в тихую ошибку.
- Взаимодействие сервисов через JWT с асимметричной подписью и JWKS не требует общего секрета и позволяет менять ключ без перезапуска Python-сервиса.
