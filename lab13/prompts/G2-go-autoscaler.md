### Что сделать

Сервис `agents/cmd/autoscaler` и пакет с логикой в `agents/internal/`:

1. **Политика** — чистая функция без ввода-вывода: по `backlog` (`num_pending +
   num_ack_pending` консьюмера), текущему числу экземпляров, времени последнего роста
   очереди и параметрам (`per_instance`, `min`, `max`, `cooldown`) возвращает желаемое
   число экземпляров. Рост — сразу (сколько нужно, не по одному), уменьшение — только
   после `cooldown` без роста очереди и не ниже `min`. Учти, что `min` экземпляров
   запущены вне автомасштабировщика (статические из compose/скрипта) и он ими не
   управляет: управляет только «добавочными».
2. **Наблюдение** — раз в `interval` читает `ConsumerInfo` консьюмера `step-<step>`
   потока `TASKS` для каждого управляемого шага (JetStream API `nats.go/jetstream`).
   Если консьюмера ещё нет — шаг пропускается без ошибки.
3. **Бэкенды** за интерфейсом:
   - `exec` — запускает локальные процессы агента (`путь к бинарнику агента -role <файл роли>`)
     с `AGENT_ID=<step>-auto-<n>` и тем же окружением; при уменьшении шлёт сигнал
     остановки (на Windows `os.Process.Kill` после неудачной мягкой остановки — агент
     должен успеть доделать задачу: JetStream перевыдаст неподтверждённую задачу после
     AckWait); отслеживает завершившиеся процессы;
   - `docker` — Docker Engine API напрямую через `net/http` по unix-сокету
     `/var/run/docker.sock` (без SDK Docker): создать контейнер из образа агента с
     командой роли, окружением и сетью compose (параметры из окружения/конфига),
     запустить; при уменьшении — остановить с таймаутом и удалить. Метки контейнеров
     `mas.autoscaler=1`, `mas.step=<step>`; при старте подхватить уже запущенные свои
     контейнеры (после рестарта автомасштабировщика не плодить лишние).
4. **Конфигурация** — YAML-файл (`-config deploy/autoscaler.yaml` или аналог): бэкенд,
   интервал, список шагов с `role` (путь к файлу роли), `per_instance`, `min`, `max`,
   `cooldown`; для docker — образ, сеть, переменные окружения агента. Создай пример
   `deploy/autoscaler.local.yaml` (exec, шаг `triage`, `per_instance: 5`, `max: 3`) и
   `deploy/autoscaler.docker.yaml`.
5. **Наблюдаемость** — события `scaled_up`/`scaled_down` в `events.autoscaler` по
   контракту (summary: шаг, backlog, было → стало), спаны `autoscaler.reconcile`
   (сервис `autoscaler`), логи slog. HTTP `GET /status` (порт из конфига, по умолчанию
   8090) — JSON с текущим backlog и экземплярами по шагам (для дашборда).
6. Graceful shutdown: по сигналу останавливает **свои** добавочные экземпляры.

## Почему так

- Политика отделена от наблюдения и бэкендов: решение «сколько экземпляров» проверяется
  тестами без NATS и Docker.
- Бэкенд `exec` нужен, потому что Docker локально нет; `docker` — требование задания,
  проверяется в CI через compose.
- Уменьшение с задержкой (`cooldown`) — чтобы не «дёргать» экземпляры на пилообразной
  нагрузке.
