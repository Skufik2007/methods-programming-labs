# Архитектура: конвейер сбора и анализа данных датчиков здоровья

Документ — контракт между компонентами. Форматы, ключи etcd, субъекты NATS, схема Arrow
и API эмулятора обязательны для Go-, Rust- и Python-кода.

## 1. Конвейер

```
                     ┌──────────── etcd: членство, шарды, чекпоинты ────────────┐
                     │                                                          │
sensorsim (Go) ──HTTP──► collector ×N (Go) ──┬─► JSONL-файлы (raw / agg) ──► Python: Polars ─► Parquet ─► DuckDB ─► графики
  эмулятор датчиков      опрос горутинами,   ├─► NATS JetStream VITALS ────► Python: потоковый анализ (скользящее окно 5 мин) ─► дашборд (WebSocket)
                         буфер, окна         └─► Arrow Flight (DoGet) ─────► Python: клиент Arrow ─► Polars
                                                          ▲
                          Rust-валидатор (PyO3) используется на шаге очистки в Python
```

| Компонент | Язык | Каталог |
|---|---|---|
| Эмулятор датчиков `sensorsim` | Go | `go/cmd/sensorsim` |
| Сборщик `collector` | Go | `go/cmd/collector` |
| Валидатор `vitals_validate` | Rust + PyO3 | `rust/vitals_validate` |
| Анализ (ETL), клиент Arrow | Python | `python/vitals/analytics` |
| Потоковый анализ | Python | `python/vitals/streaming` |
| Дашборд реального времени | Python (FastAPI + WebSocket) | `python/vitals/dashboard` |
| Сборщик на Python (для сравнения) | Python (asyncio + aiohttp) | `python/vitals/pycollector` |

## 2. Предметная область и данные

Вариант 22 — «Сбор и анализ медицинских данных», источник — носимые датчики здоровья
(эмуляция). Каждое устройство (`device_id`) закреплено за пациентом (`patient_id`) и
снимает несколько показателей.

| `metric` | Единица | Допустимый диапазон (валидация) | Норма покоя (для генерации) |
|---|---|---|---|
| `heart_rate` | `bpm` | 25–250 | 60–90 |
| `spo2` | `%` | 50–100 | 95–99 |
| `temperature` | `C` | 30.0–43.0 | 36.3–37.0 |
| `systolic_bp` | `mmHg` | 50–260 | 105–135 |
| `diastolic_bp` | `mmHg` | 30–160 | 65–85 |
| `resp_rate` | `breaths/min` | 4–60 | 12–18 |
| `steps` | `count` | 0–400 (за интервал) | 0–30 |

### 2.1 Сырое показание (raw), одна строка JSONL

```json
{"device_id": "dev-0001", "patient_id": "p-0001", "seq": 123,
 "ts": "2026-10-13T09:30:00.250Z", "metric": "heart_rate", "value": 72.0,
 "unit": "bpm", "battery": 87}
```

- `seq` — номер показания устройства, строго растёт с 1 (все метрики устройства в общей
  нумерации).
- `ts` — RFC 3339 UTC с миллисекундами.
- `value` — число или `null` (сбой датчика).
- `battery` — 0–100 или `null`.

### 2.2 Дефекты, которые эмулятор вносит намеренно (для очистки и валидации)

Доли задаются конфигурацией, по умолчанию 1–3% каждая:
- выход за допустимый диапазон (`heart_rate: 999`, `spo2: -1`);
- `value: null`;
- дубликат — повторная выдача уже отданного `seq` в следующем ответе;
- пустая или неверная единица (`unit: ""`, `"BPM"`);
- `ts` из будущего (+1 ч) — сбой часов устройства.

### 2.3 Клинические эпизоды

Для аналитики эмулятор детерминированно генерирует эпизоды у части пациентов:
тахикардия (ЧСС > 120), десатурация (SpO2 < 92), лихорадка (> 38.0), гипертония
(САД > 160). Эпизод длится 1–10 минут.

### 2.4 Оконный агрегат (agg), одна строка JSONL

```json
{"window_start": "2026-10-13T09:30:00Z", "window_end": "2026-10-13T09:30:10Z",
 "device_id": "dev-0001", "patient_id": "p-0001", "metric": "heart_rate",
 "count": 10, "invalid": 1, "sum": 731.0, "min": 68.0, "max": 79.0,
 "mean": 73.1, "last": 75.0, "collector_id": "collector-1"}
```

- Окно tumbling, полуоткрытое `[window_start, window_end)`, выровнено по эпохе.
  Длительность — `WINDOW` (по умолчанию 10 с).
- В `sum`, `min`, `max`, `mean`, `last` входят только валидные значения; `invalid` —
  число отброшенных.
- Показание относится к окну по `ts`. Окно закрывается, когда время сборщика
  `now ≥ window_end + WINDOW_LATENESS` (по умолчанию 2 с). Опоздавшие показания после закрытия
  считаются в счётчике `late_dropped` и не теряются молча.

## 3. API эмулятора `sensorsim`

HTTP, JSON. Генерация детерминирована по `SEED`: показание устройства с номером `k` —
функция `(SEED, device_id, k)`. Ничего не хранится: показания вычисляются по запросу
для времени, которое уже наступило.

| Запрос | Ответ |
|---|---|
| `GET /v1/devices` | `{"devices": [{"device_id", "patient_id", "metrics": [...], "period_ms"}]}` |
| `GET /v1/devices/{id}/readings?after_seq=N&limit=M` | `{"device_id", "readings": [raw...], "last_seq"}` — до `M` (≤ 1000) показаний с `seq > N`, уже «случившихся» к текущему моменту |
| `GET /healthz` | `{"status": "ok"}` |
| `GET /metrics` | счётчики в формате Prometheus (запросы, выданные показания) |

Параметры (окружение): `DEVICES` (по умолчанию 100), `PERIOD_MS` (интервал устройства,
1000), `SEED`, `LATENCY_MS` (искусственная задержка ответа с джиттером: при ней
параллельный опрос даёт выигрыш), доли дефектов, `START` (момент начала, по умолчанию —
старт процесса), `ADDR`.

## 4. Сборщик `collector`

- Опрашивает свои устройства (раздел 5) пулом горутин. `WORKERS` по умолчанию 16,
  интервал `POLL_INTERVAL` 1 с.
- Показания идут в канал с буфером `BUFFER` (10000).
- Пакетная запись: накопить `BATCH_SIZE` (500) записей или ждать `FLUSH_INTERVAL` (2 с),
  смотря что наступит раньше.
- Стоки (включаются конфигурацией, можно несколько):
  1. **files** — JSONL в `OUT_DIR/raw/<collector_id>-<YYYYMMDDHH>.jsonl` и
     `OUT_DIR/agg/<collector_id>-<YYYYMMDDHH>.jsonl`;
  2. **nats** — JetStream-поток `VITALS`: субъекты `vitals.raw.<device_id>` и
     `vitals.agg.<device_id>`, `Nats-Msg-Id` = `<device_id>-<seq>` для raw и
     `<device_id>-<metric>-<window_start>` для agg (дедупликация);
  3. **flight** — Arrow Flight-сервер (раздел 6).
- Режим передачи: `EMIT=raw|agg|both`. Задание 2 сравнивает объём raw и agg.
- **Graceful shutdown** по SIGINT/SIGTERM:
  - прекратить опрос;
  - дождаться обработки канала;
  - закрыть все открытые окна (с пометкой досрочного закрытия в логе);
  - сбросить буферы во все стоки;
  - записать чекпоинты;
  - отозвать lease в etcd;
  - закрыть соединения.
- **Метрики** `GET /metrics` (Prometheus-текст) и `GET /status` (JSON): опросы,
  показания, записанные байты по стокам, окна, `late_dropped`, ошибки, размер очереди,
  назначенные устройства.
- Чекпоинт устройства обновляется **после** успешной записи пакета во все стоки. При
  рестарте опрос продолжается с `after_seq` = чекпоинт. В **сыром** потоке (raw)
  сборщик дубликаты не отфильтровывает: это задача очистки в Python, она проверяется
  отдельно. **Оконный агрегатор** учитывает показание с данным `(device_id, seq)` один раз,
  иначе повтор исказил бы `count`, `sum` и `mean`. Эмулятор отдаёт показания устройства по возрастанию
  `seq`, а одно устройство опрашивается последовательно, поэтому повтором считается любой
  `seq`, не больше последнего учтённого для устройства.

## 5. Координация через etcd (задание 1)

Префикс ключей — `/lab14/`.

| Ключ | Значение | Время жизни |
|---|---|---|
| `/lab14/collectors/<collector_id>` | `{"collector_id", "flight_addr", "status_addr", "started_at"}` | lease с TTL `ETCD_TTL` (10 с), keepalive |
| `/lab14/checkpoints/<device_id>` | последний записанный `seq` (десятичное число) | постоянный |

- **Распределение устройств — rendezvous hashing (HRW).** Владелец устройства —
  сборщик с максимальным `fmix64(fnv64a(collector_id + "/" + device_id))` среди живых
  членов `/lab14/collectors/` (`fmix64` — финализатор MurmurHash3). Лидер не нужен: все
  сборщики по одному списку членов приходят к одному и тому же разбиению.
  Чистый `fnv64a` без финализатора не годится (находка №2, её нашёл генератор G2). В FNV-1a
  умножение переносит изменения только в старшие разряды, а у всех ключей одинаковый
  суффикс `/dev-XXXX`. Поэтому один сборщик выигрывал у другого на всех устройствах:
  100 из 100 для `c1`/`c2`.
- Сборщик следит (watch) за префиксом членов. При изменении он пересчитывает свои
  устройства, освобождает чужие (сначала сбрасывает их буфер и чекпоинт) и подхватывает
  новые с чекпоинта.
- Пока членство «переходит», возможно краткое двойное чтение устройства. Это допустимо:
  дубликаты по `(device_id, seq)` убирает очистка, а потери исключены, потому что
  чекпоинт пишется после записи.
- Чекпоинт пишется транзакцией «записать, только если новое значение больше старого». Так
  старый владелец не откатит чекпоинт назад.

## 6. Arrow (задание 3)

Сборщик держит в памяти кольцевой буфер последних записей (`FLIGHT_RETENTION`, по
умолчанию 15 мин) и отдаёт их по **Arrow Flight**.

- `DoGet` с тикетом `{"kind": "raw"|"agg", "since": "<RFC 3339>"}` (JSON) возвращает поток
  RecordBatch по 8192 строки.
- `ListFlights` описывает доступные наборы.

Схема raw:

| Поле | Тип Arrow |
|---|---|
| `device_id` | `dictionary<int32, utf8>` |
| `patient_id` | `dictionary<int32, utf8>` |
| `seq` | `int64` |
| `ts` | `timestamp[ms, UTC]` |
| `metric` | `dictionary<int32, utf8>` |
| `value` | `float64` (nullable) |
| `unit` | `utf8` |
| `battery` | `int16` (nullable) |

Схема agg — поля из раздела 2.4. Время — `timestamp[ms, UTC]`, счётчики — `int64`,
агрегаты — `float64`, строковые идентификаторы — словарные.

Адреса Flight-серверов Python-клиент берёт из etcd (`flight_addr` членов) или из параметра.

## 7. Потоковая обработка (задание 7)

- Поток JetStream `VITALS`: субъекты `vitals.>`, retention limits, `max_age` 24 ч.
- Python-потребитель — durable pull-консьюмер `analyzer` на `vitals.raw.>`.
- **Скользящее окно** 5 минут с шагом 10 с по каждому `(patient_id, metric)`: среднее,
  мин/макс, количество, доля невалидных.
- Правила тревог:

  | Тревога | Условие |
  |---|---|
  | `tachycardia` | среднее ЧСС за 1 мин > 120 |
  | `desaturation` | мин SpO2 за 1 мин < 92 |
  | `fever` | последняя температура > 38.0 |
  | `hypertension` | среднее САД за 5 мин > 160 |
  | `sensor_fault` | доля невалидных за 5 мин > 20% |

- Результат публикуется в core NATS: `vitals.stats` — снимок раз в 2 с; `vitals.alerts` —
  при срабатывании и при снятии тревоги.

## 8. Дашборд (задание 8)

FastAPI + WebSocket.
- `GET /` — страница.
- `WS /ws` — поток снимков и тревог (JSON).
- `GET /api/snapshot` — последний снимок.
- `GET /api/alerts?limit&offset` — тревоги.

Дашборд подписан на `vitals.stats` и `vitals.alerts`. Требования:
- строгая CSP (`script-src 'self'`);
- графики рисуются собственным JS на `<canvas>` без CDN;
- данные выводятся через `textContent`, без `innerHTML`.

## 9. Аналитика в Python (ETL)

`python -m vitals.analytics run --source files|flight --in data/ --out data/out/`:

1. **Загрузка.** JSONL через `pl.scan_ndjson` или Arrow Flight через `pyarrow.flight` →
   Polars; вывод `head`, схемы, числа строк, пропусков.
2. **Очистка** (каждый шаг документирован и считает затронутые строки):
   - удалить дубликаты по `(device_id, seq)`;
   - нормализовать `unit`;
   - отбросить `ts` из будущего;
   - валидировать диапазоны через Rust-валидатор (раздел 10);
   - пропуски `value` удалить, `battery` заполнить последним известным по устройству;
   - привести типы.
3. **Агрегаты** по пациенту и метрике (SUM, AVG, MIN, MAX, COUNT), почасовые профили,
   эпизоды по правилам раздела 7.
4. **Сохранение** — Parquet: `clean/` партиционирован по `metric`, плюс `agg.parquet`.
5. **DuckDB** — SQL к Parquet (фильтр, группировка, сортировка, оконные функции).
   Тот же анализ в Polars; время обоих замеряется.
6. **Визуализация** (Plotly HTML + PNG через matplotlib): временной ряд ЧСС и SpO2
   пациента с эпизодами, гистограмма распределения, тепловая карта «пациент × час», доля
   дефектов по типам.

## 10. Rust-валидатор (задание 4)

Модуль `vitals_validate` (PyO3, сборка maturin):

```python
validate_columns(metric: list[str] | numpy, value: numpy.float64[], unit: list[str]) -> numpy.uint8[]
```

Возвращает код причины для каждой строки:

| Код | Причина |
|---|---|
| 0 | ок |
| 1 | `null` / NaN |
| 2 | вне диапазона |
| 3 | неизвестная метрика |
| 4 | неверная единица |

Диапазоны — из таблицы раздела 2, зашиты в Rust и экспортируются функцией `ranges()`.
У Python-обёртки есть **чистая реализация на Polars** с тем же контрактом: она служит для
сравнения скорости и как запасной вариант, если модуль не собран. Результаты обеих
реализаций должны совпадать на одних данных (проверяется тестом).

## 11. Kubernetes (задание 5)

Манифесты в `k8s/`: sensorsim, etcd (1 реплика), NATS, collector (Deployment) и
HPA (`autoscaling/v2`, CPU 60%, 1–4 реплики). Сборщики масштабируются горизонтально без
настройки: новые реплики регистрируются в etcd, и HRW перераспределяет устройства.
Проверка в CI — кластер kind с metrics-server: рост нагрузки на эмуляторе
(`DEVICES` ↑, `LATENCY_MS` ↓) → CPU сборщиков ↑ → HPA увеличивает число реплик.

## 12. Замеры (обязательны для повышенного уровня)

`python -m vitals.bench ...` пишет результаты в `reports/bench/*.json` и графики в
`reports/img/`:

| Что сравнивается | Метрики |
|---|---|
| Go- и Python-сборщик при одинаковой нагрузке (устройства, задержка) | показаний в секунду, пиковая RSS, CPU |

| Rust-валидатор и чистый Polars | время на 1 млн строк |

## 13. Общие требования

- Конфигурация — только переменные окружения и флаги. Подключения создаются в `main` или
  фабриках, а не при импорте.
- Логи: Go — `log/slog` JSON; Python — JSON-строки в UTF-8.
- Время — UTC. Часы в коде инжектируются, чтобы тестировать окна и чекпоинты.
