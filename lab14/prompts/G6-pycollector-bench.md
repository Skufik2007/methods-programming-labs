### Что сделать

1. **`python/vitals/pycollector/`** — сборщик на asyncio + aiohttp, функционально равный
   Go-сборщику в режиме `COORD=static`, `SINKS=files`, `EMIT=raw|agg|both`: опрос устройств
   с ограничением параллелизма (`WORKERS`), `after_seq`, буфер, пакетная запись JSONL того
   же формата (байт-в-байт совместимые поля), tumbling-окна раздела 2.4, graceful shutdown,
   флаг `--duration`. Окна — переиспользуй/напиши чистый класс (не копируй код из
   `vitals/streaming`, если он там есть: там скользящее окно, здесь tumbling).
2. **`python/vitals/bench/`** — `python -m vitals.bench <сценарий>`, результаты в
   `reports/bench/<сценарий>.json`, графики в `reports/img/`:
   - `collectors`: Go и Python сборщики против одного эмулятора при одинаковых `DEVICES`
     (например 50, 200, 500) и `LATENCY_MS` (0 и 20): показаний/с, пиковая RSS и CPU
     (`psutil`, опрос процесса раз в 200 мс), по 3 прогона, медиана; каждый прогон —
     свежий `OUT_DIR`; проверка, что оба собрали сопоставимое число показаний;
   - `transport`: JSONL против Arrow Flight на одном наборе (raw и agg): байты на диске / по
     сети, время передачи и загрузки в Polars (Flight-клиент — из `vitals.analytics`);
   - `raw_vs_agg`: объём и число записей raw против agg при `WINDOW` 10 с и 60 с;
   - `validation`: Rust (`vitals.validation`) против чистого Polars на 1 млн строк;
   - `report`: собрать всё в `reports/bench/summary.md` (таблицы + ссылки на графики).
   Бинарники Go — `go/bin/` (собрать `go build -o go/bin/ ./go/cmd/...`), Go — в
   `D:\dev\go\bin`; запуск процессов — `subprocess` с явными путями, остановка — флаг
   `-duration`/`--duration` (не сигналы: Windows).
3. Сценарии должны работать и на Linux (CI) — пути через `pathlib`, бинарники с расширением
   `.exe` только на Windows.

## Почему так

- Одинаковая функциональность Python- и Go-сборщика — иначе сравнение нечестное.
- Медиана трёх прогонов и свежий каталог — шум ОС и кэш файлов не должны решать исход.
- Остановка по флагу длительности: на Windows сигналы фоновым процессам ненадёжны.

## Ответ генератора (итоговое сообщение, сокращено)

Файлы: `python/vitals/pycollector/` (те же переменные окружения, что у Go; только `files` и
`COORD=static`; `TumblingAggregator`; `/metrics`, `/status`, `/healthz`; остановка с fsync и чекпоинтами),
`python/vitals/bench/` (`stats` — медиана, `summarize_runs`, коэффициент сокращения; сценарии
`collectors`, `transport`, `raw_vs_agg`, `validation`, `report`). Совместимость: raw-строки Python и Go
совпали побайтно на общем префиксе; agg — одинаковое число записей (420 на 20 устройствах).

Быстрые прогоны генератора (`--quick`, не медиана): collectors 200 устройств — Go 77 102 / Python 74 502
показаний/с при 0 мс (RSS 36 / 74 МБ), 67 801 / 80 502 при 20 мс; validation — Polars 142 мс, Rust 80 мс;
raw_vs_agg (Go) — окно 10 с: сокращение 8,0× по записям и 4,6× по байтам, окно 60 с: 37,2× и 21,0×;
transport — raw JSONL 149,5 Б/строку, Flight 46,6 Б/строку.

Отклонения генератора: в `collectors` эмулятор стартует с накопленными за 6 часов данными, поэтому `EMIT=raw`;
`transport` сравнивает удельные величины (наборы не совпадают до строки); Python проверяет `BATCH_SIZE`
после ответа, а не после показания; экранирование `\b`/`\f` отличается от Go.
